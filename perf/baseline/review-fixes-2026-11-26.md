# 评审修复后的性能验证（2026-11-26）

## 环境与方法

- Windows `10.0.26300`，.NET `10.0.15`，8 个逻辑处理器
- 基线 `75b1916`，候选为六个评审修复提交
- 同机交替运行；主目标格 5 轮、保护格 3 轮，预热 5 秒、测量 20 秒

## 主目标格：QoS 1 / 100 / 64 KiB（5 轮）

| 指标 | 基线 | 候选 | 变化 |
|---|---:|---:|---:|
| 端到端吞吐 | 45.44 msg/s | 45.04 msg/s | -0.9% |
| 发布 p99 中位数 | 46,044 µs | 50,554 µs | +9.8% |
| 交付 p99 中位数 | 39,132 µs | 39,704 µs | 1.015× |

逐轮吞吐：基线 `44.6 / 45.0 / 45.4 / 48.1 / 47.4`，候选 `43.0 / 34.9 / 45.0 / 48.9 / 50.2`。
门禁通过（吞吐 ≥0.95×、交付 p99 ≤1.05×）。

先跑的 3 轮版本得到 -13.4% 与交付 p99 1.312，候选单轮在 35–54 msg/s 之间摆动；
扩到 5 轮后回到 -0.9%。这台机器在该格上的轮次噪声大于门禁阈值，3 轮不足以判定。

## 保护格：QoS 0 / 100 / 8 KiB（3 轮）

吞吐 `+1.9%`（基线 `338.5 / 336.4 / 275.2`，候选 `342.8 / 345.3 / 245.5`），
交付 p99 比值 `1.459`。

该格的交付 p99 在本机一直不可复现：此前四次对比的比值是 0.63 / 1.53 / 1.92 / 3.16，
同一份代码的相邻轮次能差 2–3 倍（`deadline-scheduling-2026-11-26.md`）。本轮
同样只能得出"吞吐未回退"，p99 不判定。

## 过期内存斜率：QoS 0 / 1 订阅者 / 1 KiB / 过期 300 秒（180 秒运行）

| 变体 | 端到端吞吐 | Broker 峰值工作集 | Broker 私有字节 | Broker CPU 总时长 |
|---|---:|---:|---:|---:|
| 基线（无压缩） | 7,070 msg/s | 132.8 MB | 107.3 MB | 373.2 s |
| 候选（阈值压缩） | 6,851 msg/s | **94.2 MB** | **37.5 MB** | 366.3 s |

峰值工作集下降 **29%**，私有字节下降 **65%**，CPU 与吞吐基本持平（吞吐 -3.1%）。
这直接对应修复项：基线把每条已投递但未到期的消息对象一直挂在堆里，
180 秒约 120 万条；候选在陈旧条目超过阈值时重建索引，把它们释放。

## 结论

- 主目标格通过门禁；保护格吞吐未回退，p99 因既有噪声不可判定。
- 过期索引压缩的内存收益有直接证据（180 秒内私有字节 107 MB → 37 MB）。
- 其余修复（ACK 校验、写门限时、retained 读取与恢复、订阅差量、卫生项）由
  661 个单元/集成测试覆盖，不涉及吞吐假设。
