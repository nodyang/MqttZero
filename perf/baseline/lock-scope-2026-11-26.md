# 连接写序列与控制面锁收窄（2026-11-26）

## 环境与方法

- Windows `10.0.26300`，.NET `10.0.15`，8 个逻辑处理器
- 基线：`76a307d`（锁改造前），候选：锁改造后的 HEAD
- 同机交替运行，基线/候选各 3 轮，预热 5 秒、测量 20 秒，`max-pending 1024`
- 客户端：MQTTnet 5.2.0，单发布者
- 命令：`MqttZero.BrokerBenchmarks ab`，两个变体只差提交

改造内容：每连接写门（`PipeWriter` 单写者）、路由提交不再跨存储 I/O、
retained 独立锁。写门只在回退路径上产生竞争，正常负载下是一次无竞争
信号量进出。

| QoS 0 / 100 / 8 KiB | 355.49 | 360.64 | +1.4% | 1,219 / 929 | 504,836 / 581,106 | 1.151 | 0 / 0 / 0 |

门禁判定：

- 主目标格（QoS 1 / 100 / 64 KiB）通过：吞吐未回退，发布 p99 改善 2.6%，
  交付 p99 比值 0.966。
- 保护格（QoS 0 / 100 / 8 KiB）吞吐未回退，发布 p99 改善 24%，但交付 p99
  比值 1.151 超过 5% 门限，**判定为不确定而不是通过**。

## 保护格的不确定性证据

该单元格的交付 p99 在基线侧三轮分别是 `1,000,000 / 402,622 / 504,836 µs`，
跨度超过 2 倍，且第一轮撞上直方图 1 秒上限；候选侧为
`610,983 / 581,106 / 534,661 µs`。用两次独立复跑确认：

- 2 轮 10 秒诊断：基线 `277.1 / 340.0 msg/s`、交付 p99
  `1,000,000 / 460,256`；候选 `333.1 / 353.8 msg/s`、交付 p99
  `650,609 / 987,684`，吞吐 +11.3%，交付 p99 比 1.122。
- 一次 5 轮 20 秒复跑在测量排空阶段超时（30 秒排空上限），未产生结果；
  这是该单元格在 8 核机器上排空抖动，不是候选侧独有现象。

因此该格只能得出「吞吐与发布 p99 未回退」，交付 p99 需要更长测量窗口或
更严格的排空契约才能下定论。改造本身不触碰 QoS 0 出站路径的语义。
